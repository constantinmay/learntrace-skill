# LearnTrace 工作流方案讨论稿

状态：待团队讨论，尚未成为正式产品决策，也不作为当前 Skill 或 CLI 的实现契约。

## 讨论背景

当前项目文档采用“集中整理方案”：在一次分析流程中读取项目材料和授权轨迹，提取证据、提出候选学习节点、让学生确认并生成档案。

另一种可讨论的方向是“检查点方案”：学生在开发开始和阶段节点主动触发记录，最后再汇总报告。本文介绍两种方案，并形成检查点方案草案，供团队比较；本文不修改现有项目陈述、架构和分工约定。

## 方案一：集中整理方案

### 基本流程

```text
本地 Git 仓库、项目文档、既有测试日志、授权的 AI 轨迹
                            ↓
                     静态解析与轨迹适配
                            ↓
                     可观察事件和候选
                            ↓
                  学生确认、补充或否认
                            ↓
                    Markdown 学习档案
```

### 主要特点

- 以一次完整分析为主，适合项目阶段结束后的集中复盘。
- 静态材料解析与 OpenCode 等宿主轨迹适配是明确的输入环节。
- 学生主要在候选学习节点形成后集中确认。
- 实现路径直接，容易用固定样例验证端到端输出。

### 优点

- 与现有项目陈述、初始架构和四人分工一致。
- 状态管理较少，首个原型容易实现和演示。
- 可以在没有持续记录机制的情况下处理已有项目。
- 轨迹适配器、静态解析器和报告模块边界直观。

### 风险与限制

- 项目结束后回顾可能遗漏当时的决策背景和失败过程。
- 大量候选集中出现时，学生确认负担可能较高。
- 输入材料不完整时，只能标记“未记录”，难以在开发过程中及时补充。
- 若过早依赖某个 AI 宿主轨迹，MVP 范围可能被适配工作牵制。

## 方案二：检查点方案

### 基本流程

```text
首次建档                     阶段复盘（可重复）             汇总输出
init → 学生正常开发 → reflect → 继续开发 → reflect → report
```

### 主要特点

- 由学生主动触发，不要求后台持续监听。
- 将范围确认、阶段反思和最终汇总拆开。
- 每次只处理上一个检查点之后的新增证据。
- 候选学习节点在阶段发生后及时由学生确认、补充或否认。
- AI 轨迹可以作为授权后的可选证据，不是所有检查点的必需输入。

### 优点

- 更容易保留阶段决策、失败尝试和修正过程。
- 每次确认内容较少，降低项目结束时的集中复盘负担。
- 学生能够在证据尚新鲜时纠正系统候选。
- 后续增加 Hook 或 Plugin 时，可以复用检查点记录和报告模型。

### 风险与限制

- 需要设计项目状态、检查点游标、重复执行和失败恢复。
- 学生可能忘记运行 `reflect`，仍会出现记录空档。
- 增量 Git 和文件变化的边界比一次性扫描更复杂。
- 三个命令及其产物会增加 schema、测试和跨模块联调成本。

## 两种方案的主要差异

| 比较项 | 集中整理方案 | 检查点方案 |
| --- | --- | --- |
| 触发时机 | 项目阶段结束后集中运行 | 初始化、阶段节点和最终汇总分别运行 |
| 状态管理 | 可以接近无状态 | 必须保存项目基线和检查点状态 |
| 学生确认 | 一次集中确认 | 每个阶段少量确认 |
| 轨迹适配 | MVP 中的明确输入环节 | 可选证据，是否进入 MVP 待讨论 |
| 过程完整性 | 依赖已有材料是否完整 | 有机会在开发过程中及时记录 |
| 实现复杂度 | 较低 | 较高 |
| 既有项目适用性 | 较好 | 需要设计首次建档时的历史范围 |
| 未来实时扩展 | 需要补充状态模型 | 可在检查点模型上增加 Hook |

## 检查点方案草案

以下内容只用于讨论，不冻结命令名称、文件格式或 schema 字段。

### 1. `init`：建立项目基线

目标：明确系统可以读取什么、不能读取什么，并建立后续增量整理的起点。

建议流程：

1. 只读发现 Git 仓库、候选项目材料和既有测试证据。
2. 展示候选分析范围、敏感内容风险和建议排除项。
3. 由学生确认范围、排除项，以及是否授权读取 AI 轨迹。
4. 保存项目配置和初始检查点。
5. 向学生说明何时适合运行下一次阶段反思。

候选产物：

- 项目内使用指南，例如 `LEARNTRACE.md`。
- 结构化项目配置，例如 `.learntrace/project.json`。

待讨论：是否必须生成使用指南、配置是否进入 Git、首次检查点选择当前 HEAD 还是包含历史区间。

### 2. `reflect`：整理阶段证据

目标：整理上次成功检查点以来的新增证据，并及时取得学生回应。

建议流程：

1. 读取已确认的项目范围和上次成功检查点。
2. 只读收集范围内的 Git、文件、文档和既有测试证据。
3. 仅在本次获得明确授权时读取可选 AI 轨迹。
4. 形成带来源引用的可观察事实。
5. 提出少量候选学习节点，每项附依据和不确定性。
6. 由学生确认、补充或否认候选，并分别保存系统候选和学生回应。
7. 完整保存阶段记录后，再推进检查点。

候选产物：阶段记录目录，例如 `.learntrace/journal/`。

待讨论：候选数量上限、交互中断后的恢复方式、没有新增证据时是否写空记录、文件未提交变化如何确定边界。

### 3. `report`：汇总学习档案

目标：从项目基线和阶段记录中生成可编辑的学习档案。

建议流程：

1. 读取项目配置和全部有效阶段记录。
2. 汇总可观察事实及其来源。
3. 只把学生确认过的学习节点写成结论。
4. 将否认、未确认候选和缺失证据保持为非结论状态。
5. 生成本地 Markdown 档案，由学生审阅后决定是否分享。

候选产物：例如 `learning-portfolio.md`。

待讨论：报告是否覆盖旧文件、是否支持时间范围、否认记录是否出现在最终档案、分享版是否属于 MVP。

## 共同证据与隐私边界

无论采用哪种方案，都应保持现有原则：

- 可观察事实必须引用 Git、文件、文档、既有日志或经授权的轨迹。
- 系统候选必须附依据和不确定性，不能自动成为学习结论。
- 学生确认、补充和否认必须与系统候选分开保存。
- 证据不足时使用“未记录”，不得补全事件。
- 不执行被分析仓库中的代码、测试或日志命令。
- 完整 AI 对话只有在学生明确授权时才能读取。
- 不做作弊检测、作者归因、贡献排名或自动评分。

## 建议评估方式

团队可以用同一组脱敏样例分别演练两种方案，并比较：

1. 实现一个可信端到端样例所需的工作量。
2. 学生确认候选所需的时间和问题数量。
3. 事实、候选和确认是否能稳定回溯。
4. 材料缺失和中断场景下是否会产生错误结论。
5. OpenCode 轨迹适配是否必须进入 M1 关键路径。
6. 四条任务线能否在 schema 冻结后并行开发。

## 需要团队决定的问题

1. M1 采用集中整理、检查点，还是先集中整理再演进到检查点？
2. 如果采用检查点，三个命令名称是否确定为 `init`、`reflect`、`report`？
3. 项目配置和阶段记录是否提交到项目 Git？
4. OpenCode 轨迹适配是 M1 必需项还是后续扩展？
5. `schema v0` 是否现在就需要包含检查点状态？
6. 谁负责跨模块状态管理和最终集成？

在这些问题形成团队结论前，不应据此修改正式架构、团队分工或 Skill 工作流。
