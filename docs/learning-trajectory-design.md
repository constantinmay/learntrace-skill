# LearnTrace 学习轨迹与复盘设计讨论稿

> 状态：讨论稿，尚未作为实现规范。
>
> 本文记录在 PR #14 审阅问题修复完成后，通过真实 OpenCode 运行和
> `example.zip` 输出对比发现的新产品问题：底层证据与审计能力已经较完整，
> 但 Skill 生成的学习内容仍然空洞，尚未形成真正可用的学习轨迹。

## 1. 为什么需要重新讨论学习轨迹

当前实现已经能够收集并保存：

- Git 提交与文件变化；
- 项目文档；
- 既有测试日志；
- 经用户授权的 OpenCode 轨迹；
- 系统候选、用户确认和来源索引。

问题不再只是“能不能生成文件”，而是生成结果能不能帮助人理解：

- 项目经历了哪些阶段；
- 每个阶段想解决什么问题；
- 过程中出现了哪些反馈、失败或约束变化；
- AI 在什么场景参与；
- 用户进行了哪些选择、修改和验证；
- 哪些内容可以称为学习收获，哪些仍然缺少证据。

现有两种输出分别暴露了不同问题：

- main 输出信息量大，但接近机器审计记录的直接打印，内部 ID、重复候选和
  泛化问题过多；
- 当前 PR 分支对弱关联进行严格过滤后，报告更短，却只剩下少量泛化内容，
  无法承载真实的项目复盘。

使用同一份 `example.zip/local` 证据进行对比时：

- main：202 条事实、13 个候选、449 行 Markdown，约 75 KB；
- 当前分支：202 条事实、1 个候选、87 行 Markdown，约 5 KB。

这说明问题不在于原始事实数量不足，而在于事实到人类叙事之间缺少合适的
中间层。

## 2. 产品定位

LearnTrace 的主要用户是使用 AI 编程工具完成课程项目、希望复盘和展示自己
项目过程的人。

次要阅读者可以是教师、助教、导师或项目评审，但他们不是产品的控制者。

产品目标是：

> 从 Git、项目文档、测试证据和经过授权的 AI 轨迹中，还原项目过程，帮助
> 用户识别、补充和表达有证据支持的学习经历，并生成由用户拥有和控制的
> 可分享档案。

产品不负责：

- 作弊检测；
- 作者归因；
- AI 与用户贡献比例；
- 能力排名或自动评分；
- 根据工具次数判断理解程度；
- 根据时间相邻关系断言 AI 导致某个提交。

## 3. 方法论基础及其适用边界

本文不是照搬某个机构的完整方案，而是从多个成熟原则中提取适合 LearnTrace
的部分，再结合项目约束形成自己的设计。

### 3.1 任务理解、目标计划、实施监控、评价调整

MIT Teaching + Learning Lab 将元认知过程概括为计划、监控和评价，并提供了
面向任务、策略、进展和结果的具体提示。与其一致的 Winne–Hadwin 自我调节
学习模型进一步区分四个可递归阶段：

1. 理解任务；
2. 设置目标并制定计划；
3. 实施策略并监控进展；
4. 评价结果并调整后续策略。

这一过程适合作为软件项目复盘的骨架，但不能仅凭工具日志自动识别所有阶段
中的内在判断。

参考：

- [MIT Metacognition](https://tll.mit.edu/teaching-resources/how-people-learn/metacognition/)
- [A Review of Self-regulated Learning: Six Models and Four Directions for Research](https://pmc.ncbi.nlm.nih.gov/articles/PMC5408091/)

### 3.2 材料、反思与证据

Stanford 的 ePortfolio 实践强调：代码、提交、文档等是材料；用户对材料的
解释为材料赋予意义；经过选择和组织的材料与反思共同构成支持学习主张的
证据。

它还强调同一批材料可以针对不同受众形成不同版本。对 LearnTrace 的直接
启发是：

- JSON 保存完整材料；
- 主文档只选择对项目故事有意义的证据；
- 用户决定哪些解释和内容进入分享版；
- 完整档案不等于把所有记录展示给人看。

参考：

- [Stanford ePortfolios and Self-Reflection](https://teachingwriting.stanford.edu/news/eportfolios-and-self-reflection-powerful-pedagogical-tools-learning)
- [Stanford ePortfolio Capstone](https://pwrnotations.stanford.edu/academics/eportfolio-capstone)

### 3.3 从原始轨迹到有意义的过程

Trace-SRL 等轨迹研究指出，原始操作和频次不能直接代表学习过程，需要先将
细粒度事件映射成有理论意义的行动序列。相关研究也表明，操作轨迹与口述或
自述只能覆盖彼此的一部分，日志不能替代用户对目标、判断和评价的说明。

LearnTrace 不需要照搬面向群体研究的聚类和过程挖掘，但应采用
“原始事件 -> 行动模式 -> 项目过程”的思想。

参考：

- [Trace-SRL](https://eric.ed.gov/?id=EJ1282877)
- [Trace-based Micro-analytic Measurement of Self-Regulated Learning Processes](https://learning-analytics.info/index.php/JLA/article/view/4535)
- [Triangulation of trace and think-aloud data](https://onlinelibrary.wiley.com/doi/full/10.1111/jcal.12801)

### 3.4 主张必须匹配证据

Evidence-Centered Design 的基本思想是：先明确希望作出什么主张，再明确需要
什么观察证据支持该主张。

在 LearnTrace 中：

- “项目增加了 REST API”可以由 Git 和文件变化支持；
- “用户因为部署便利选择了某个数据库驱动”需要用户解释；
- “AI 帮助修复了某个问题”需要明确会话语义或用户确认；
- “修改已经验证有效”需要测试日志、运行结果或用户提供的验证说明。

参考：

- [ETS Evidence-Centered Design](https://www.ets.org/Media/Research/pdf/TC-10-07.pdf)

### 3.5 少量、及时、可跳过的复盘提示

项目追踪和元认知提示更适合出现在阶段边界、反馈或问题转折处。提示时机和
频率会影响效果；无关或过密的提示可能打断当前工作。

LearnTrace 因此不应按每次工具操作或每个提交提问。问题应引用具体材料，
帮助用户回忆当时的判断，并允许直接跳过。

参考：

- [MIT Project-Based Learning Tools](https://web.mit.edu/blossoms/project_based_learning_tools_0.html)
- [CMU Exam Wrappers](https://www.cmu.edu/teaching/designteach/teach/examwrappers/)
- [Prompt timing in self-regulated learning](https://doi.org/10.1024/1010-0652.23.2.105)
- [Stimulated recall in AI-assisted programming](https://link.springer.com/article/10.1186/s40594-025-00592-w)

### 3.6 用户自主性

用户面对学习分析结果时，需要能够理解数据、修正解释、决定下一步行动，并
控制分析和分享范围。LearnTrace 应支持：

- 选择证据范围；
- 查看系统为何提出某个线索；
- 确认、补充、否认或跳过；
- 编辑主文档；
- 选择是否分享；
- 删除本地材料。

参考：

- [Four design principles for learner dashboards that support agency and empowerment](https://doi.org/10.1108/JARHE-11-2018-0251)
- [AAEEBL Data Responsibility](https://aaeebl.org/digital-ethics-principles-in-eportfolios/data-responsibility/)

## 4. LearnTrace 的核心方法

本文建议将 LearnTrace 的方法称为“证据支撑的循环复盘”
（Evidence-grounded Cyclic Reflection）。这是本项目对上述原则的综合适配，
不是外部机构已经发布的同名框架。

它遵循以下过程：

```text
可观察事实
    ↓
开发阶段
    ↓
复盘线索
    ↓
用户确认或补充
    ↓
有证据支持的复盘事件与学习收获
```

### 4.1 可观察事实

可以直接追溯的记录，例如：

- Git 提交及文件变化；
- 文档中的需求、约束和接口说明；
- 测试失败或通过记录；
- 经授权的 OpenCode 工具操作；
- 用户明确提供的原话。

事实回答“发生了什么”，不自动回答“为什么发生”。

### 4.2 开发阶段

系统按时间和功能组织事实，例如：

- 项目初始化；
- 数据模型与数据库；
- 后端接口；
- 前端基础结构；
- 功能完善；
- 调试与修复；
- 验证；
- 文档整理。

开发阶段是项目叙事，不是个人理解或学习结论。即使没有任何用户确认，系统
也应能够生成清楚、完整的阶段概览。

### 4.3 复盘线索

系统只在出现有意义的过程转换时提出线索，例如：

- 问题 -> 调整；
- 失败测试 -> 修复 -> 通过；
- AI 建议 -> 用户修改或拒绝；
- 需求变化 -> 设计调整；
- 一种实现 -> 重写或重构；
- 修改 -> 明确验证；
- 阶段评价 -> 下一步计划。

普通的 `read`、`ls`、`git log`、单次 `write` 或时间相邻的提交不能单独构成
复盘线索。

### 4.4 已确认的复盘事件

事实与用户解释结合后，才形成完整复盘事件。理想结构包括：

- 当时的任务和目标；
- 采用的方案；
- 遇到的问题或反馈；
- AI 的参与方式；
- 用户作出的选择；
- 实施结果；
- 验证方式；
- 形成的认识；
- 下一步行动。

并非每个字段都必须填写，但系统不得代写缺失的个人判断。

## 5. 两种使用模式

### 5.1 事后回顾模式

用户提供项目目录或压缩包，系统读取已有证据并生成：

- 项目开发阶段；
- 功能、修复和验证记录；
- 证据缺口；
- 少量可选复盘提示；
- 未确认版项目过程档案。

这种模式不能完整恢复当时的意图。没有用户补充时，产物应被视为“项目过程
档案”，不能把系统推测写成个人学习结论。

### 5.2 过程记录模式

Skill 在 OpenCode 上下文仍然存在时，于有意义的阶段边界建议保存轻量检查点。

适合触发检查点的情况：

- 用户说明了一个新目标；
- 一个明显功能阶段刚完成；
- 测试失败后改变方案；
- AI 建议被接受、修改或拒绝；
- 完成修复并进行验证；
- 当前会话即将结束。

检查点可以保存：

```text
当前目标
采用的方案
遇到的问题
AI 参与摘要
用户作出的选择
验证结果
下一步
```

约束：

- 写入前展示给用户；
- 可以修改、跳过或拒绝；
- 默认不保存完整聊天和代码；
- 只保存在本地；
- 不因用户跳过而作负面判断。

## 6. AI 轨迹与 Git 的关系

仓库现有架构明确规定，不推断 AI 会话与 Git 提交的对应关系。

main 的候选实现按时间将 OpenCode 工具事件与后续提交配对，即使标注“高不
确定性”，仍容易形成因果暗示，也与该约束存在冲突。

系统可以分别陈述：

- OpenCode 在某个时间编辑过 `backend/main.go`；
- Git 记录显示项目增加了后端数据层。

只有在下列条件之一成立时，才能将它们组织为同一复盘事件：

- 结构化检查点明确记录了二者关系；
- 会话语义中存在明确、经过授权的目标与结果；
- 用户主动确认了关系。

文件路径重合和时间接近可以用于发现待核查线索，但不能单独证明因果关系。

## 7. 三份主要输出

### 7.1 `learning-record.md`

面向人阅读的项目过程与复盘档案。

建议结构：

1. 项目概述；
2. 开发轨迹；
3. 有证据支持的关键复盘事件；
4. AI 协作触点；
5. 验证与质量情况；
6. 已确认的学习收获；
7. 证据边界和下一步。

正文不应包含：

- `cand-...`、`evt-...` 等内部 ID；
- 全部事实和工具日志；
- 单纯的 `bash/write/edit` 次数；
- 重复的“不确定性”模板；
- “用户回答：未填写”式空白表单；
- 未经确认的个人判断。

对于无法确认的内容，用自然语言说明证据边界，例如：

> 项目后期统一了两个接口的时间格式；当前没有对应测试日志，因此无法确定
> 问题最初的表现和修改后的验证方式。

主文档可以在末尾轻量提示存在可选复盘内容，但不在各阶段插入问题。

### 7.2 `.learntrace/learning-questions.md`

文件名可暂时保持兼容，文档标题和产品文案使用“可选复盘提示”。

规则：

- 默认不超过 3 个，证据丰富时最多 5 个；
- 每个提示只问一个核心问题；
- 必须引用具体功能、提交、文件、错误或测试；
- 明确说明可以跳过、否认或稍后补充；
- 不以缺少回答作为负面信息。

示例：

> 提交 `3eac321` 统一了新建接口和列表接口中的 `created_at` 格式，但没有发现
> 对应测试日志。这个差异最初表现为什么，你采用了什么方式验证修改结果？

### 7.3 `.learntrace/archive-records.json`

机器证据与审计层，保存：

- 全部事实；
- 来源索引；
- 完整提交哈希；
- 开发阶段关联；
- 复盘线索；
- 用户确认；
- 内容指纹；
- 解析和隐私告警。

JSON 不承担人类叙事。普通用户不需要直接阅读它，但主文档中的结论应可以
追溯到这里。

## 8. 证据链接

主文档中的链接分为两类。

项目证据链接：

- GitHub commit；
- 对应提交版本的文件；
- Issue 或 PR；
- 测试日志文件。

审计证据链接：

- 相对链接到 `.learntrace/archive-records.json`；
- 保留内部证据 ID 供程序定位，但不在正文直接展示。

普通 Markdown 对 JSON 内部对象的锚点支持不一致。首版可以实现文件级链接和
稳定 GitHub 链接；如以后提供本地证据查看器，再按事件 ID 实现精确跳转。

## 9. AI 在 LearnTrace 中的职责

适合 AI 完成：

- 将提交和文档归纳为开发阶段；
- 识别失败、调整、重写和验证等复盘线索；
- 将事实整理成自然语言；
- 根据具体证据生成少量复盘提示；
- 将用户补充自然融入主文档。

不适合 AI 完成：

- 根据工具次数判断能力；
- 根据时间相邻断言因果关系；
- 自动计算 AI 与用户贡献比例；
- 替用户编写个人反思；
- 在没有测试证据时声称功能正确；
- 将候选推断写成既成事实。

确定性模式和 LLM 模式必须遵守相同证据边界。LLM 可以改善组织和措辞，不能
改变事实等级。

## 10. 对现有实现的处理建议

应保留：

- 输入安全和异常处理；
- 隐私脱敏；
- 多 OpenCode 会话支持；
- LLM 显式启用、输出边界和失败回退；
- 缺少测试日志时明确说明；
- 事实、候选和确认分层；
- 三份主要输出；
- 完整机器审计 JSON。

需要重新设计：

- 把开发阶段和候选学习节点混为一体的推断；
- main 中只凭时间邻近建立的 AI—Git 候选；
- 当前分支中过度严格、与最小轨迹不匹配的学习信号过滤；
- 工具次数式 AI 协作概览；
- 固定只展示部分提交的阶段摘要；
- 泛化、重复的复盘问题；
- 主文档中机器化的审计表达。

## 11. 可能的数据结构演进

首轮不必立即破坏 `v0` Schema。

可以先在 reporting 内部增加 `DevelopmentStage`：

```text
DevelopmentStage
- title
- time_range
- goal_or_scope
- git_event_ids
- document_event_ids
- test_event_ids
- trace_touchpoints
- evidence_gaps
```

现有对象可以暂时继续使用：

- `ObservableEvent`：可观察事实；
- `LearningNodeCandidate`：复盘线索；
- `StudentConfirmation`：内部兼容名称，对外统一显示“用户确认”。

等实际输出和交互稳定后，再决定是否在 schema `v1` 中重命名对象、增加结构化
检查点或正式加入开发阶段。

## 12. 建议的实施顺序

本设计问题应与 PR #14 的审阅问题修复分开处理。PR #14 继续保持技术修复和
真实流程打通的范围；学习轨迹重构在独立 PR 中审查。

在修改实现前，先固定三个 golden artifacts：

1. `example.zip` 的理想未确认版 `learning-record.md`；
2. 理想的 `learning-questions.md`；
3. 对应 `archive-records.json` 中阶段、线索和来源关系的目标结构。

随后按以下顺序实施：

1. 增加开发阶段层；
2. 将阶段叙事与学习候选分离；
3. 重写主文档渲染；
4. 重写可选复盘提示；
5. 移除未经支持的 AI—Git 自动配对；
6. 增加提交、文件和审计证据链接；
7. 设计轻量结构化检查点；
8. 使用真实 OpenCode 会话和多种示例项目验证。

## 13. 验收标准

不以 Markdown 行数、事实数量或候选数量作为成功指标。

应检查：

- 阅读者能否快速说明项目的主要开发阶段；
- 每项事实是否能追溯到提交、文件、文档或测试；
- 是否把普通日志错误描述成学习；
- 是否出现未经支持的 AI—Git 因果关系；
- 复盘提示是否具体、少量且与项目相关；
- 用户完全不补充时，主文档是否仍能独立阅读；
- 用户补充后，内容是否自然融入主文档；
- 主文档是否没有内部 ID 和机器噪音；
- JSON 是否保留完整审计能力；
- 是否没有泄露密钥、个人路径或未经授权的完整对话。

建议至少使用三类项目做 golden/回归验证：

- 有 Git、文档和 OpenCode 轨迹，但没有测试日志；
- 包含失败、修复和通过测试的项目；
- 没有 AI 轨迹，只能生成普通项目过程档案的项目。

## 14. 尚待确认的产品选择

以下问题需要在实现前或实现初期确定：

- 结构化检查点是否进入第一版重构，还是作为随后的小版本；
- `DevelopmentStage` 首轮只作为 reporting 内部模型，还是进入机器 JSON；
- `learning-questions.md` 是否仅修改标题，还是在未来版本重命名；
- 主文档默认展示多少个开发阶段和复盘事件；
- GitHub remote 缺失或不是 GitHub 时，证据链接如何降级；
- 是否需要提供本地 JSON 证据查看器，或暂时只提供文件级链接。

## 15. 核心结论

LearnTrace 不应该尝试从日志中“计算用户学会了什么”。

它应该：

1. 用可信证据还原项目过程；
2. 将原始事实组织成开发阶段；
3. 在真正的转折处提出少量复盘线索；
4. 让用户决定这些线索是否构成自己的学习经历；
5. 将确认后的内容整理成可读、可分享、可追溯的档案。

一句话概括：

> LearnTrace 是证据支撑的 AI 协作项目复盘 Skill，而不是日志打印器、行为监控
> 工具或自动评价系统。
